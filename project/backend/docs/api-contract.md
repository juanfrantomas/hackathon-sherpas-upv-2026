# Financial Milestones — API contract

> **Who this is for.** The agent (or person) adapting the React client to the
> new backend. It is the complete contract: you should not need to read the
> backend source to build against it.
>
> - The machine readable contract is [`../openapi.json`](../openapi.json).
> - The TypeScript types to copy are [`milestones.types.ts`](./milestones.types.ts).
> - The examples under [`examples/`](./examples/) are **real answers** captured
>   from a running instance, not written by hand.

---

## 1. Quick start

```bash
cd project/backend
make install          # creates .venv and installs the dependencies
cp .env.example .env  # add AI_API_KEY (and MCP_TOKEN when you have one)
make migrate          # creates the SQLite schema
make dev              # http://127.0.0.1:8001
```

The interactive documentation is served at `http://127.0.0.1:8001/docs`.

Point the client at it:

```
# .env.local of the frontend
VITE_MILESTONES_API_URL=http://127.0.0.1:8001
```

The backend answers CORS requests from `http://localhost:5173` out of the box
(`CORS_ORIGINS` in `.env`). If you serve the frontend on another port, add it
there.

The backend reads the plan from the Sherpas MCP when it has a token, and from
the offline case files in `cases/` otherwise. The four demo households are
`timothy-melanie-weah`, `michael-carter`, `daniel-emily-johnson` and
`samantha-lewis`.

## 2. Authentication

**There is none.** This is a prototype decision, not a production answer.

What exists instead is an **allowlist of case identifiers** (`ALLOWED_CASE_IDS`
in the backend `.env`). A request for a case outside the list is refused with
`403 CASE_NOT_ALLOWED` **before** the backend talks to the MCP or to the AI.

Two consequences for the client:

- Do not treat a `caseId` as a credential. The backend decides which cases it
  serves.
- Do not ship this to production. The backend binds to `127.0.0.1` and is
  meant to run next to the client on a private machine.

## 3. The domain in one page

```
                      ┌──────────────────────────────────────────┐
                      │  the financial plan (MCP / cases/*.json)  │
                      └───────────────────┬──────────────────────┘
                                          │  read + normalised into a digest
                                          ▼
                      ┌──────────────────────────────────────────┐
                      │        milestones  (generated by AI)      │
                      │  title · why · action · category · type  │
                      │  priority · tasks · due_date · checkin   │
                      └───────────────────┬──────────────────────┘
                                          │
              ┌───────────────────────────┼───────────────────────────┐
              ▼                           ▼                           ▼
        ┌───────────┐             ┌─────────────┐            ┌──────────────┐
        │   tasks   │             │ observations│            │  check-ins   │
        │ to do    │             │ MCP + client│            │ monthly      │
        └─────┬─────┘             └──────┬──────┘            └──────┬───────┘
              │ done                     │ figures                 │ review
              ▼                          ▼                         ▼
        ┌───────────┐             ┌─────────────┐            ┌──────────────┐
        │ progress  │             │  progress   │            │ notifications│
        └───────────┘             └─────────────┘            └──────────────┘
```

**Milestone** — one personalised step for the household: understand, review or
decide something (an *educational* milestone) or reach a measurable financial
result (a *financial* milestone).

**Task** — one concrete action inside a milestone. Tasks have a persistent id,
an order, a required flag and a done flag. Nothing more.

**Observation** — a measured financial value, either read from the plan
(`source: "mcp"`) or declared by the household (`source: "client"`). Both are
kept side by side and neither overwrites the other.

**Check-in** — a scheduled **review**. It is *not* the deadline of the
milestone; that is `due_date`. The first review is proposed by the AI, the
next ones follow a deterministic monthly rule.

**Notification** — an internal notice about a pending review or an overdue
milestone. The backend creates them on its own; the client only reads and
marks them as read.

## 4. The milestone contract

```jsonc
{
  // --- legacy contract: the prototype already used these, do not rename ---
  "id": "ms_329f10ade5f90b72",
  "title": "Agree how to allocate the cash surplus above your emergency reserve",
  "why": "About $60,222.50 of your accessible cash sits above recommended reserves.",
  "action": "Review the surplus and agree a prioritized allocation plan.",
  "section": "summary",
  "status": "in_progress",
  "checkin": "Dec 23",

  // --- everything else ---
  "case_id": "timothy-melanie-weah",
  "category": "Financial Planning",
  "type": "educational",
  "priority": "high",
  "tasks": [ /* see §6 */ ],
  "task_progress": 50,
  "financial_progress": null,
  "financial_progress_state": "not_quantifiable",
  "financial_metric_key": null,
  "financial_direction": null,
  "financial_start_value": null,
  "financial_target_value": null,
  "financial_unit": null,
  "financial_currency": null,
  "due_date": "2026-12-16",
  "checkin_pending": false,
  "checkin_date": "2026-12-23",
  "overdue": false,
  "source": [
    {
      "part": "financial-health",
      "section": "narrative",
      "json_path": "financial-health.narrative.summary",
      "quote": "About $60,222.50 sits above the emergency reserve."
    }
  ],
  "created_at": "2026-11-16T20:21:39Z",
  "updated_at": "2026-11-16T20:21:39Z",
  "completed_at": null,
  "last_reviewed_at": null
}
```

| Field | Type | Null? | What it means |
|---|---|---|---|
| `id` | string | no | Stable identifier. It does not depend on the order of the list. |
| `title` | string | no | What the milestone is about. |
| `why` | string | no | Why it matters to this household. |
| `action` | string | no | What to do next. Never an instruction to move money. |
| `section` | enum | no | The plan section the household opens: `summary`, `retirement`, `assets`, `debt`, `savings`, `protection`. |
| `status` | enum | no | `not_started`, `in_progress`, `completed`, `on_hold`, `cancelled`. |
| `checkin` | string | yes | **Display format** such as `"Dec 23"`. Use `checkin_date` for logic. |
| `case_id` | string | no | The household. |
| `category` | enum | no | One of the 11 categories of §9. |
| `type` | enum | no | `educational` or `financial`. |
| `priority` | enum | no | `high`, `medium`, `low`. |
| `tasks` | Task[] | no | The steps of the milestone. |
| `task_progress` | number | **yes** | Share of the required tasks that are done. `null` when the milestone has no required task: *not applicable*, which is different from 0. |
| `financial_progress` | number | **yes** | Share of the financial goal that is reached. `null` whenever a percentage would be an invention (see §8). |
| `financial_progress_state` | enum | no | `not_quantifiable`, `on_track`, `achieved`, `regressed`, `conflicting`. |
| `financial_metric_key` | string | yes | The metric the milestone is measured on, for example `liability_chase_cc`. |
| `financial_direction` | enum | yes | `increase` or `decrease`. |
| `financial_start_value` | string | yes | Decimal **string**: `"18000.00"`. |
| `financial_target_value` | string | yes | Decimal **string**: `"11200.00"`. |
| `financial_unit` / `financial_currency` | string | yes | `"USD"`, `"USD"`. |
| `due_date` | string | yes | Target date, `YYYY-MM-DD`. Independent of the check-in. |
| `checkin_pending` | boolean | no | A review was planned and the date has passed. |
| `checkin_date` | string | yes | The next review, `YYYY-MM-DD`. |
| `overdue` | boolean | no | `due_date` has passed and the milestone is still open. It is an indicator, not a status. |
| `source` | SourceRef[] | no | Where the recommendation comes from in the plan. |
| `created_at` / `updated_at` | string | no | ISO 8601, UTC. |
| `completed_at` | string | yes | When the household closed it. |
| `last_reviewed_at` | string | yes | When the last review happened. |

Money arrives as a **decimal string**, not a float, so nothing is lost on the
way. Parse it with `Number(value)` only for arithmetic; keep the string for
display.

## 5. The milestones

### 5.1 List the milestones of a case

```
GET /api/cases/{case_id}/milestones
```

| Query | Values | Meaning |
|---|---|---|
| `group_by` | `none` (default), `category` | Adds `grouped_by_category` to the answer. |
| `status` | one of the 5 statuses | Only these. |
| `category` | one of the 11 categories | Only these. |
| `type` | `educational`, `financial` | Only these. |
| `priority` | `high`, `medium`, `low` | Only these. |

The answer holds **every** milestone of the case; there is no pagination.

```jsonc
{
  "milestones": [ /* Milestone */ ],
  "meta": {
    "case_id": "timothy-melanie-weah",
    "count": 9,
    "stale": false,
    "stale_reason": null,
    "data_source": "local",
    "last_successful_sync_at": "2026-11-16T20:21:39Z"
  },
  "grouped_by_category": null
}
```

`meta.stale` is `true` when the data may be older than the plan — for example
when the MCP could not be reached and the backend answered from its offline
copy. Show a small notice ("these figures may be out of date") and keep
working; the milestones themselves are still valid.

Example: [`examples/milestones-list.json`](./examples/milestones-list.json)

### 5.2 Read one milestone

```
GET /api/cases/{case_id}/milestones/{milestone_id}
```

Example: [`examples/milestone-detail.json`](./examples/milestone-detail.json)

### 5.3 Change the status

```
PATCH /api/cases/{case_id}/milestones/{milestone_id}/status
{ "status": "in_progress" }
```

Only the household changes the status, and only along these transitions:

| From | To |
|---|---|
| `not_started` | `in_progress`, `on_hold`, `cancelled` |
| `in_progress` | `completed` (through `/complete`), `on_hold`, `cancelled` |
| `on_hold` | `in_progress`, `cancelled` |
| `completed` | `in_progress` (reopening) |
| `cancelled` | `not_started` (reopening) |

Anything else answers `409 INVALID_STATUS_TRANSITION`.

Example: [`examples/milestone-status-changed.json`](./examples/milestone-status-changed.json)

### 5.4 Confirm the completion

```
POST /api/cases/{case_id}/milestones/{milestone_id}/complete
{ "confirmed": true, "note": null }
```

`confirmed` **must** be `true`, otherwise the answer is `409`. Completing a
milestone is a statement by the household, not something the backend infers.

### 5.5 The operational progress

```
GET /api/cases/{case_id}/milestones/{milestone_id}/progress
```

```jsonc
{
  "milestone_id": "ms_329f10ade5f90b72",
  "task_progress": 50,
  "required_tasks": 2,
  "completed_required_tasks": 1,
  "optional_tasks": 1,
  "completed_optional_tasks": 0,
  "auto_completable": false
}
```

`auto_completable` is `true` when completing the remaining tasks is enough to
close the milestone — which only happens for educational milestones.

### 5.6 The progress of the whole case

```
GET /api/cases/{case_id}/progress
```

Example: [`examples/case-progress.json`](./examples/case-progress.json)

## 6. Tasks

### 6.1 List them

```
GET /api/cases/{case_id}/milestones/{milestone_id}/tasks
```

```jsonc
{
  "id": "task_550bd8e53af34eb7",
  "title": "List the priority uses and the plan's suggested amounts",
  "description": null,
  "order": 0,
  "is_required": true,
  "status": "completed",
  "origin": "ai",
  "completed_at": "2026-11-16T20:21:39Z"
}
```

### 6.2 Complete, uncomplete or edit one

```
PATCH /api/cases/{case_id}/milestones/{milestone_id}/tasks/{task_id}
{ "status": "completed" }
```

- `status` is `"completed"` or `"pending"`; the same call does both.
- The call is idempotent: completing twice changes nothing.
- **The answer is the milestone**, not the task, because completing a task can
  change the progress and can even close an educational milestone.

### 6.3 Add and remove one

```
POST   /api/cases/{case_id}/milestones/{milestone_id}/tasks
{ "title": "Call the bank on Monday", "description": null, "is_required": false }

DELETE /api/cases/{case_id}/milestones/{milestone_id}/tasks/{task_id}
```

A task created by the household carries `origin: "client"` and is never
replaced by a later synchronisation.

## 7. The rules that surprise people

### 7.1 An educational milestone closes itself

When **every required task** of an educational milestone is done, the backend
closes it: the status becomes `completed` and `completed_at` is set. There is
no extra call to make.

A **financial** milestone never closes itself, not even when all its tasks are
done. Closing it is a statement about money, so it needs
`POST …/complete` with `confirmed: true`.

An educational milestone **without** required tasks also needs the explicit
confirmation: there is nothing to infer it from.

### 7.2 `null` is not zero

`task_progress: null` means "this milestone has no required task", so there is
no progress to show. `financial_progress: null` means the milestone has no
measurable goal, or that the figures cannot be compared, or that the plan and
the household disagree. **Never render `null` as 0 %.**

### 7.3 A check-in is a review, not a deadline

`checkin` / `checkin_date` is when the household should **look at the
milestone again**. `due_date` is when it should be **done**. They are
independent: many milestones have no `due_date` at all.

A review that was planned and whose date has passed sets
`checkin_pending: true` and produces a notification.

### 7.4 The reviews are monthly and deterministic

The AI proposes the **first** review only. Every later one is
`previous + 1 month`, calculated by the backend (a 31 January review becomes
28 February). Registering the same review twice does nothing.

### 7.5 The figures have two sources and they can disagree

A milestone with a measurable goal holds an **initial value** (what the plan
states) and a **target value**. The household can declare what it really has
with `POST …/observations`.

When the two sources disagree by more than 1 %, the backend keeps **both**,
reports `state: "conflicting"` and returns `progress: null`. It never picks
one silently and never shows a percentage that looks verified.

Example: [`examples/financial-progress.json`](./examples/financial-progress.json)

## 8. Financial observations

### 8.1 Declare a value

```
POST /api/cases/{case_id}/milestones/{milestone_id}/observations
{
  "metric_key": "liability_chase_cc",
  "metric_type": "balance",

  "unit": "USD",
```

## 11. Generating and synchronising

### 11.1 Generate the milestones

```
POST /api/cases/{case_id}/milestones/generate
{ "force": false }
```

The first access to a case generates them automatically, so this endpoint is
mostly for a demo or a regeneration. It answers `409 SYNC_CONFLICT` when the
case already has milestones, unless `force` is `true`.

### 11.2 Synchronise with the plan

```
POST /api/cases/{case_id}/sync
{ "force": false }
```

A synchronisation reads the plan again, compares it with the last version and
only asks the AI for new milestones when something changed. When nothing
changed, **no AI call is made** and the milestones are left untouched.

The synchronisation never deletes a milestone, never reopens a completed one
and never loses a completed task, even when the AI rewrites it.

### 11.3 Read the state

```
GET /api/cases/{case_id}/sync
```

Example: [`examples/sync-state.json`](./examples/sync-state.json)

## 13. The pillars

Four views of the same plan. The figures come from the plan itself; the words
are written by the model, so a pillar can answer with its figures and no
prose when the model is unreachable (`"generated": false`).

```jsonc
  "case_id": "timothy-melanie-weah",

  "simulated_score": 73,
  "score_delta": 13,
  "synergy_detected": true,
```

## 14. The live voice

```
WS /api/voice/ws/{case_id}?model=gemini-3.8-live&style=auto&partner=both&topic=…&greet=1
```

The browser records the microphone and the backend relays it to the realtime
model of the proxy. The first message is the session:

```jsonc
{
  "type": "session_ready",
  "case_id": "timothy-melanie-weah",
  "model": "gemini-3.8-live",
  "voice": "Aoede",
  "style_key": "refranero",
  "style": "Cercana, Familiar y con Refranes",
  "is_couple": true,
  "couple_members": [ /* … */ ],
  "message": "Conectado con voz 'Aoede' · Registro: …"
}
```

Then, in both directions:

| Message | Direction | Payload |
|---|---|---|
| `input_audio_buffer.append` | browser → backend | `{ "audio": "<base64 PCM 16 bit, 24 kHz>" }` |
| `user_text` | browser → backend | `{ "text": "…" }` |
| `switch_partner` | browser → backend | `{ "partner": "melanie" }` |
| `tool_call` | backend → browser | `{ "section": "financial-health.score" }` |
| `response.output_audio.delta` | backend → browser | `{ "delta": "<base64 PCM>" }` |
| `response.output_audio_transcript.delta` | backend → browser | `{ "delta": "…" }` |

The models are `gemini-3.8-live`, `gpt-realtime-2.1-mini` and
`gpt-realtime-2.1`.

## 17. Errors

Every error uses the same envelope:

```json
{ "error": { "code": "MILESTONE_NOT_FOUND", "message": "…", "details": {} } }
```

| Code | HTTP | What the client should do |
|---|---|---|
| `CASE_NOT_ALLOWED` | 403 | The case is not served by this instance. Show the demo data. |
| `INVALID_CASE_ID` | 400 | The identifier is malformed. |
| `MILESTONE_NOT_FOUND` | 404 | It was deleted or the id belongs to another case. |
| `TASK_NOT_FOUND` | 404 | Same for a task. |
| `INVALID_STATUS_TRANSITION` | 409 | The transition is not allowed; refresh and offer the allowed ones. |
| `INVALID_FINANCIAL_OBSERVATION` | 422 | The value, unit or date is not acceptable. |
| `SYNC_CONFLICT` | 409 | A synchronisation is already running. |
| `MCP_UNAVAILABLE` | 503 | The plan could not be read. The milestones that are stored are still served, with `meta.stale: true`. |
| `MCP_AUTH_ERROR` | 503 | The MCP token expired. The backend answers from its offline copy. |
| `FINANCIAL_PLAN_NOT_FOUND` | 404 | Unknown household. |
| `AI_PROVIDER_UNAVAILABLE` | 503 | The AI is unreachable. Nothing was changed. |
| `AI_INVALID_RESPONSE` | 502 | The AI answered something unusable. Nothing was changed. |
| `AI_RESPONSE_TOO_LARGE` | 502 | The answer was truncated. Nothing was changed. |
| `DATABASE_ERROR` | 500 | The write failed and was rolled back. |
| `VALIDATION_ERROR` | 422 | The body or the query is not valid; `details.errors` lists the fields. |
| `GENERATION_DISABLED` | 503 | The instance does not generate milestones. |

**The important rule:** when the MCP or the AI is down and the milestones are
already stored, the client still gets them. The answer carries
`meta.stale: true` and `meta.stale_reason`. Never substitute invented figures.

---

## 18. What the backend does **not** do

- No authentication, no accounts, no roles.
- No email, no SMS, no push notifications. The notices are internal.
- No pagination: a case has a handful of milestones, the whole list fits.
- No file upload and no evidence.
- No advisor approval: closing a milestone is the household's word.
- No change to the financial health score.
- No financial operation is ever executed.

## 19. Contract deltas against the current client

The prototype reads its milestones from the static
`src/features/family/data/families.ts`. Four things change.

### 19.1 The statuses

The client declares `not_started | in_progress | completed | needs_review`
(`src/features/family/types.ts:9`). The API has `on_hold` and `cancelled`
instead of `needs_review`.

```ts
// before
export type MilestoneStatus = 'not_started' | 'in_progress' | 'completed' | 'needs_review'

// after — take the API type and derive the prototype one
import type { MilestoneStatus as ApiMilestoneStatus } from '../services/milestones.types'

export type MilestoneStatus = ApiMilestoneStatus
export type MilestoneDisplayStatus = MilestoneStatus | 'needs_review'

/** The prototype's fourth state is derived, never stored. */
export function displayStatus(m: Milestone): MilestoneDisplayStatus {
  if (m.status === 'completed' || m.status === 'cancelled') return m.status
  return m.checkin_pending || m.overdue ? 'needs_review' : m.status
}
```

`src/components/ui/statusMeta.ts` keeps its four entries; map the two new
API statuses onto it (`on_hold` → "On hold", `cancelled` → "Cancelled").

### 19.2 The check-in date

`checkin` stays the display string (`"Dec 23"`), so `MilestoneItem.tsx:47`
does not change. Use `checkin_date` when you need to compare dates.

### 19.3 The two progress fields

`task_progress` and `financial_progress` can be `null`. Render "—" and not
"0 %", and use `financial_progress_state` to explain why
(`conflicting` → "the plan and your figures disagree").

### 19.4 The data is not static any more

The milestones come from the API. `meta.stale` is the only new thing the
listing adds on top of the array.

## 20. Integration recipe

Six steps, in this order. The path of every file is relative to
`project/frontend`.

### 1. Add the environment variable

`src/services/config.ts` already reads `VITE_MENTOR_API_URL`; add a sibling
`VITE_MILESTONES_API_URL` in the same file and in `.env.example`.

### 2. Copy the types

Copy `docs/milestones.types.ts` to
`src/features/family/services/milestones.types.ts`.

### 3. Write the client

Copy the shape of `src/features/family/services/mentorApi.ts` — same
`AbortSignal.timeout`, same `MentorApiError` idea — into a new
`src/features/family/services/milestonesApi.ts`:

```ts
export async function listMilestones(caseId: string): Promise<MilestoneListResponse>
export async function setMilestoneStatus(caseId: string, milestoneId: string, status: MilestoneStatus): Promise<Milestone>
export async function completeMilestone(caseId: string, milestoneId: string): Promise<Milestone>
export async function setTaskStatus(caseId: string, milestoneId: string, taskId: string, status: TaskStatus): Promise<Milestone>
export async function listNotifications(caseId: string): Promise<NotificationListResponse>
```

The `caseId` is the slug of the case (`family.caseId` in `families.ts`), for
example `timothy-melanie-weah`.

### 4. Replace the static data

`src/features/family/data/families.ts` keeps the plan sections, the story and
the mentor script; the `milestones` array of each household is replaced by the
answer of the API.

### 5. Move the state changes to the API

`src/features/family/state/familyReducer.ts` currently changes the status in
memory (`set_milestone_status`). The reducer keeps its shape but the action
calls the API and only updates the state with the answer.

### 6. Show the two new indicators

`MilestoneItem.tsx` is where `checkin_pending` and `overdue` become visible;
`ProgressScreen.tsx` is where the grouping by category and the case progress
belong.
